# Evaluación de las soluciones propuestas para edición de texto

Entorno comprobado: .NET 10, Avalonia 12.1.1, PDFsharp (escritura) y Poppler (renderizado/extracción). La propuesta es una guía de arquitectura; sus ejemplos no son código directamente intercambiable con este proyecto.

| Propuesta | Evaluación y aplicación |
| --- | --- |
| Alinear el editor por la línea base | Aplicada en páginas sin rotación. Se usa `TextLayout.Baseline`, que incluye las métricas reales del texto compuesto por Avalonia, en lugar de calcular únicamente el ascenso de una fuente. Se elimina el borde y el padding del editor y la reducción automática del tamaño de letra. |
| Extraer `Tc`, `Tw`, `Tz` y `Ts` | Aplicada a bloques nativos compatibles, de una línea, fuentes estándar y matrices de posición sin escala ni giro. Las cajas incluyen espaciado y escala; `Ts` modifica la línea base. `Tc` y `Tz` se muestran mediante LetterSpacing y escala horizontal; se conservan al escribir, junto con `Tw`. Los estados externos no triviales siguen rechazándose. |
| Aplicar tanto `Tc` como `Tw` a LetterSpacing | No es adecuado: LetterSpacing añade espacio entre caracteres; `Tw` actúa exclusivamente sobre espacios. Se mantienen separados. La vista previa todavía no reproduce un `Tw` arbitrario por palabra; el PDF sí lo conserva. |
| Interpretar toda CTM y matriz de texto | No se habilita para matrices generales: requiere interpretar la pila gráfica, XObjects, recortes y codificación de glifos. Relajar las comprobaciones sin ese intérprete produciría posiciones erróneas. Se conserva la ruta de compatibilidad existente. |
| Cargar cualquier fuente incrustada en FontManager | No se aplica de forma indiscriminada. Un subconjunto puede carecer de cmap Unicode o de los nuevos glifos; FontFile3 puede contener CFF que no es un TTF independiente. Además hay que enlazar códigos CID, CMap y ToUnicode. El motor nativo actual admite fuentes estándar; las restantes usan la sustitución existente. No se garantiza identidad tipográfica con esos PDF. |
| Reconstruir párrafos | Aplicada al doble clic en líneas nativas compatibles: misma fuente, estilo, tamaño, color, escala y espaciado entre caracteres, margen izquierdo alineado, solapamiento horizontal e interlineado uniforme entre 1 y 1.6 veces el tamaño. Se conserva el interlineado y se abre el conjunto como un bloque. No se agrupan automáticamente líneas vectoriales de compatibilidad ni páginas rotadas. |
| Detectar justificación por geometría | Aplicada con al menos tres líneas y márgenes coincidentes en todas salvo la última, con tolerancia de 1.5 pt. Es una heurística; el PDF no declara intención de párrafo. |
| Reflujo con las métricas de la fuente PDF | Aplicado para fuentes estándar, incluyendo `Tc`, `Tw` y `Tz` al calcular el ancho. Se conservan los saltos explícitos de párrafo y se evita contar espacios sobrantes al ajustar la línea. Una palabra indivisible puede exceder el ancho. |
| Escribir justificación con `Tw` o `TJ` | Se usa `Tw` para el motor nativo WinAnsi/StandardEncoding; cada línea intermedia reparte el ancho restante y la última de cada párrafo usa `0 Tw`. Cada línea escrita queda en un BT/ET independiente, con estado aislado por q/Q, para seguir siendo editable al reabrir. No se añade escritura CID/TJ general sin un motor de codificación CID. |
| Sustituir TextBox por un control de glifos propio | Se conserva TextBox, usando TextLayout para la medición y su soporte de ajuste y justificación. Un control propio necesita implementar selección, caret, IME, accesibilidad y el mismo shaping del escritor PDF. Cambiar solo el dibujo no garantiza igualdad. La equivalencia visual del 100% propuesta no puede afirmarse con dos motores y fuentes sustitutas. |
| Ocultar el texto mientras se edita | Se conserva el enmascarado existente, extendido a la caja del párrafo. Sigue siendo una máscara blanca: fondos coloreados o gráficos detrás pueden verse tapados. Eliminar temporalmente operadores para generar una vista previa limpia requiere una ruta de renderizado adicional. |
| Renderizar con la escala del monitor | No se multiplican las coordenadas de la interfaz por RenderScaling: Avalonia trabaja en unidades independientes de dispositivo. Se mantiene el render de página de 1600 px; una política de renderizado adaptativa al zoom/DPI es una mejora independiente. |

El reemplazo de párrafo valida las huellas de todas las líneas y se realiza como una transacción con restauración ante fallo y una sola entrada de deshacer. Se valida guardado/reapertura, texto extraíble, justificación, espaciado y restauración del estado anterior mediante pruebas.

Referencias: [TextLayout de Avalonia](https://docs.avaloniaui.net/api/avalonia/media/textformatting/textlayout), [operadores PDF](https://pdfa.org/download-area/cheat-sheets/OperatorsAndOperands.pdf).

Validación final: compilación Desktop correcta y 132 pruebas aprobadas, excluyendo tres pruebas de OCR que fallaron al intentar la suite completa por falta de Tesseract/modelos. No se realizó verificación visual interactiva del editor en esta sesión. La expansión de un párrafo no desplaza automáticamente los bloques posteriores de la página.
